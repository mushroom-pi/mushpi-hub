## Build-context layout

- The Docker build context is **this repository's root** (the `mushpi-ops` checkout). The `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `.env.example`, and `.github/workflows/publish.yml` all live here; `COPY mushpi-server/...` and `COPY mushpi-client/...` reach the siblings because they are materialized **inside** this root.
- Never move the `Dockerfile`/compose back into `mushpi-server/` — the cross-repo `COPY` would no longer reach `mushpi-client/`.
- **The build context is normally this repo's root — with one deliberate exception.** A parent context (the directory holding `mushpi-ops`, whose sub-repos are the developer's own working copies) is used by the local demo stack and is sound *only because* `Dockerfile.dockerignore` / `Dockerfile.mock.dockerignore` exist (see §Local demo stack). A parent context with **no** ignore file is the old prohibition and still must be avoided: the whole orchestration tree — `.git`, ~1.4 GB of sibling `node_modules`, `.env`, sibling checkouts — is swept into the upload. Do not generalise "context = this repo's root" into "never a parent directory": the invariant is *every context needs its ignore file*.
- **`.dockerignore` has load-bearing entries — never "clean it up" by pattern.** `mushpi-server/` and `mushpi-client/` are the build inputs (`COPY`ed by the Dockerfile) and must **never** be listed there; `release.json` must stay un-ignored. `mushpi-grow` and `mushpi-mock` **stay** listed even though no `Dockerfile` `COPY`s them: `publish.yml` checks both out *into this root* on `v*` tag builds (tag-gated, for the `verify-release.sh` parity check) and the local verify recipe clones them, so the entry is a no-op on a branch push and real context-trimming on exactly those paths. `mushpi-docs` is deliberately **absent** — nothing materializes it here. Beyond the repos, the file also carries the usual VCS / dependency / secret / IDE exclusions; the operative rule is only that nothing a `COPY` reads may match. To check a change, extract every `COPY`/`ADD` source from the `Dockerfile` and confirm it is not matched — note `git check-ignore` reads `.gitignore`, **not** `.dockerignore`, so it is the wrong tool for this and gives misleading hits (the sibling clones are gitignored by design).
- **Provenance, so this is not re-litigated:** the sub-repo entries were authored on 2026-09-06 at the *orchestration root* (commit `c1de1d0`, beside `be-pico-hub` and `.opencode`, both since deleted) and imported verbatim by `5732f33` when the release machinery moved into this repo — hence their root-layout flavour. Grow and mock remain functional there; the `mushpi-docs` line was removed once the audit showed nothing ever materializes that clone.
- **A per-Dockerfile ignore file replaces the shared one — it does not merge.** BuildKit prefers `<dockerfile>.dockerignore` when it exists, and that file becomes the *entire* ignore set for that build. That is why `Dockerfile.mock` ships `Dockerfile.mock.dockerignore`: the shared `.dockerignore` excludes `mushpi-mock/` (correct for the hub, which never builds it), so the mock build would have an empty context. The mock's list is therefore full-replacement, and anything the shared file excludes for the hub must be repeated there if that build needs it. **`mushpi-mock` must stay listed in the shared `.dockerignore`** — it is not a hub build input, and removing it only bloats the hub context.
- Consequence for edits: a change to `.dockerignore` does **not** reach the mock build, and a change to `Dockerfile.mock.dockerignore` does not reach the hub. Check both when either moves.
- **Three ignore lists now govern builds and only two of them are read per build: `.dockerignore`, `Dockerfile.dockerignore`, `Dockerfile.mock.dockerignore`. `<dockerfile>.dockerignore` REPLACES the shared file, it does not merge** — so `Dockerfile.dockerignore` exists in practice for both context roots, and the shared `.dockerignore` is read by no build any more. Keep `.dockerignore` and `Dockerfile.dockerignore` rule-for-rule mirrored (the file's own header says so); a divergence silently changes the CI/release build. Empirical rule for any change: extract every `COPY`/`ADD` source and confirm no pattern matches it in **all three** files — `git check-ignore` reads `.gitignore` and is the wrong tool here.

## Yarn Berry 4 / Corepack

- The sub-repos are Yarn Berry 4, not Yarn 1. They pin Yarn via `"packageManager": "yarn@4.14.1"` in each `package.json` and rely on Corepack to run the pinned release. The official `node:*` images ship Yarn 1 **and** remove/disable Corepack, so the Dockerfile must `RUN corepack enable` in **every** stage.
- Never `npm install -g yarn@4`. The `yarn` npm package is Yarn 1; Yarn 2+ is Corepack-only. Without Corepack, `yarn workspaces focus` and `yarn install --immutable` fail.

## `better-sqlite3` native build

- Needs `python3 make g++` in the **runtime** stage only, installed before `yarn workspaces focus --all --production`. Its install script tries a prebuilt binary, then falls back to `node-gyp rebuild`, which needs Python and a C++ compiler.
- The `client-build`/`server-build` stages do **not** need the toolchain — they install full dev dependencies, where prebuilds suffice.

## Client API regeneration + the `tsc` gate

- `mushpi-client/src/api/generated/*` is gitignored, so the client-build stage regenerates it from the committed `mushpi-server/spec/openapi.json` (`yarn gen:client && yarn gen:schemas`). `openapi-generator-cli` needs a JRE (`default-jre-headless`).
- The client's `yarn build` (`tsc`) is a hard gate. If the server's committed spec is missing fields (entities lacking `@ApiProperty`), the regenerated types are incomplete and the build fails. That is a **server contract bug — flag it, don't hack around it**.

## Entrypoint & runtime details

- The server entrypoint is `dist/src/main.js`, not `dist/main.js` — tsc's `rootDir` is the project root because `docs/` and `spec/` are in the compile set. `CMD ["node", "dist/src/main.js"]`.
- `APP_SECRET` is optional (LAN/Tailscale is the auth boundary), which is why the HEALTHCHECK sends no Authorization header.
- `PICO_ANNOUNCE_SECRET` is required in production and belongs in `.env`.

### Entrypoint & data directory

- The runtime `ENTRYPOINT` is `scripts/docker-entrypoint.sh`. The image has **no `USER` directive** — it starts as root so the entrypoint can fix a host bind-mount the Docker daemon created as `root` (a fresh clone has no `./mushpi-data`, and the daemon creates a missing bind-mount source root-owned). It then drops privileges and `exec`s the CMD as `node` (UID/GID 1000, matching Raspberry Pi OS's default `pi` user).
- As root it `mkdir -p`s `/data`, `/data/images` and `/data/logs`, and for each one — only when the top-level owner is not already `node:node` — runs `chown -R node:node`. The `stat` guard keeps the recursive walk off the steady-state restart path.
- A failed `chown` (read-only mount, or a filesystem that maps root to an unprivileged user such as NFS `root_squash`) exits 1 telling the operator to pre-create the directory as UID/GID 1000 on the host.
- Ownership alone is not trusted: the entrypoint verifies `/data` is writable *as `node`* (`setpriv … test -w`) before dropping, so a permission surprise fails loudly instead of surfacing inside the app.
- **Do not "simplify" this back to an assert-only guard.** The earlier never-chown version made `docker compose up` fail on every fresh clone — the reported first-run bug.
- Unprivileged starts stay guarded: `docker run --user <non-root>` skips the root branch, and an unwritable/root-owned `/data` exits 1 with the host remedy `sudo chown -R <uid>:<gid> <MUSHPI_DATA_DIR>`.
- No-volume fallback: run the image with no `/data` mount and the baked tree (created and owned in the runtime stage) still passes — `docker run ghcr.io/mushroom-pi/mushpi` boots fine for smoke tests; data just doesn't persist.
- An override command passed to `docker run` (e.g. `docker run … bash`) is still guarded: ownership is fixed, privileges dropped, then it is `exec`ed.
- **Consequence of the root start: `docker exec` now lands as root, not `node`.** PID 1 still runs as `node`; only the exec default changed. Pass `--user node` when it matters.

## `APP_HTTPS_ENABLED` (browser-facing HTTPS)

- Interpolated from `.env` and passed **into** the container as `APP_HTTPS_ENABLED: ${APP_HTTPS_ENABLED:-false}`. Unlike `MUSHPI_DATA_DIR`/`MUSHPI_IMAGE_TAG` it is a runtime env var, not interpolation-only. It declares the browser-facing deployment; it does **not** configure TLS.
- Keep it `false` (the default) for any plain-HTTP deployment — a LAN Pi is one. When `true`, the server sends `Strict-Transport-Security` and retains the CSP `upgrade-insecure-requests` directive; when `false` it sends neither.
- **On an HTTP deployment `true` breaks the UI.** `upgrade-insecure-requests` makes the browser rewrite the SPA's own asset URLs to `https://` with no HTTP fallback, so the page renders blank white with no API calls and the console reports `SSL_ERROR_RX_RECORD_TOO_LONG` (TLS spoken to a plaintext port). Browsers exempt `localhost` as a trustworthy origin, which is why it bites a LAN hostname/IP but not local dev.
- Set it `true` only when TLS is genuinely terminated in front (Tailscale Serve, a reverse proxy) or served directly.
- Server-side detail (the schema flag, the middleware, the HSTS/CSP gating) lives in `mushpi-server/REFERENCE.md`.

## Rate limiting (`MAX_REQUESTS` / `MAX_REQUESTS_TIME`)

- Throttling is **opt-in**: it registers only when **both** vars are set as positive integers — `MAX_REQUESTS` (requests per window) and `MAX_REQUESTS_TIME` (window length in **milliseconds**). Recommended starting values `MAX_REQUESTS=300` / `MAX_REQUESTS_TIME=60000` (≈5 req/s sustained per client IP), shipped commented out in `.env.example`. With the pair absent the server registers no throttler: no 429s and **no `X-RateLimit-*` headers at all**. Setting **only one** is a configuration error — the server fails at boot rather than half-configuring the guard.
- The pair is **deliberately not hard-coded** in `docker-compose.yml` or the `Dockerfile`: a hard default would silently override the server's opt-in design with no clean off switch, and would surface as unexplained 429s on the dashboard's read endpoints. Activation is operator-side only — compose passes `.env` through the service's `env_file`, so uncommenting the pair in `.env` is the entire mechanism.
- The tracker is **per client IP, per container instance**: in-memory, resets on restart/redeploy, not shared across replicas.
- The server does **not** enable Express `trust proxy`, so behind a reverse proxy every client appears to come from the proxy's IP and shares one bucket — size the limit accordingly, or leave the pair unset.
- Route scope: `/health` is always exempt (`@SkipThrottle()`), so the container HEALTHCHECK can never be rate limited; `/ping` and the `/v1/*` application routes are throttled only when the pair is configured.
- Server-side detail (the Joi pair validation, the throttler factory, the guard and header semantics) lives in `mushpi-server/REFERENCE.md`.

## `release.json` in the build context

- The client-build stage bakes `__APP_RELEASE_VERSION__` into the SPA from `release.json` (the sidebar footer). Keep **both** halves: `COPY release.json /app/release.json` in the Dockerfile **and** `release.json` absent from `.dockerignore`.
- Breaking either half fails **silently** — the image still builds, but the footer shows its `dev` fallback with no build error. The two halves are coupled.

## Tag & CI semantics

- **Neither publish workflow has ever actually executed.** No `v*` tag has been cut and `release.json` is still pre-1.0, so `publish.yml` has never run and `publish-dev.yml` is brand new. CI edits are therefore **unverified until a real run**: a wrong action owner (`actions/setup-qemu-action` instead of `docker/setup-qemu-action`) sat undetected in `publish.yml` from the day it was written. Verify every `uses:` owner against the registry (`git ls-remote --tags https://github.com/<owner>/<repo> refs/tags/<tag>`) rather than trusting the file's own history, and remember `actionlint` cannot lint composite actions.

- The image name is `ghcr.io/${{ github.repository_owner }}/mushpi`, deliberately decoupled from this repo's name. Renaming this repo does **not** rename the published image; changing the image name is a deliberate product decision, not a side effect of a repo rename.
- A `vX.Y.Z` tag pins only **this repo's** files (Dockerfile, compose, CI, `release.json`). Sub-repos build at their **default-branch HEAD**, not at any ref the tag records — so sub-repo release commits (including `mushpi-mock`) must be pushed **before** the tag.
- On tag builds CI checks out all four sub-repos and runs `scripts/verify-release.sh` (the parity check), which cross-checks the manifest against each sub-repo's committed version. Grow and mock are checked out solely so that check can run; they never enter the image.
- **`latest` is emitted by two independent mechanisms — changing one and not the other surprises you.** `publish.yml` passes metadata-action `flavor: latest=auto` (the action's default; it now travels through the shared composite action), which generates `latest` for tag-type rules — so a `v*` tag push moves `latest` on its own. The workflow's explicit `type=raw,value=latest` rule covers pushes to `main`, and its condition is bound **by ref** (`github.ref == 'refs/heads/main'`) rather than to the repository's default-branch setting — so which branch is the default cannot enable or disable it.

## Dev / pre-release image builds

- `publish-dev.yml` is `workflow_dispatch`-only. Inputs: `ops_ref` (default `main`), `server_ref`/`client_ref` (blank = that repo's default branch), a required free-form `image_tag`, and `push` (default true; false = build without pushing — multi-platform cannot `load`, so nothing is exported).
- Tag rules: `latest` and a strict `vX.Y.Z` (or `X.Y.Z`) are rejected so a dev run can never be mistaken for a release; pre-release forms (`0.9.0-rc1`) pass. Every build also gets `dev-sha-<short>` (metadata-action concatenates `prefix=dev-sha-` with the 7-char SHA verbatim). `flavor: latest=false` guarantees `latest` is never emitted.
- The release-manifest guard and `scripts/verify-release.sh` are deliberately skipped — a dev build is not a bundle release.
- Run a dev image on the Pi: set `MUSHPI_IMAGE_TAG=<tag>` in `.env`, then `docker compose pull && docker compose up -d`.
- Pre-release convention: an `0.9.0-rc1` image is a test candidate only; the actual release is cut by the `v0.9.0` git tag plus the `release.json` bump through `publish.yml`. Never retag an rc image as the release — rebuild on the tag.
- Cleanup of dev tags is **manual only** (no scheduled workflow, no retention policy): delete stale versions in the GHCR package UI or API.

## Shared build action (`.github/actions/build-image`)

- The composite action is **deliberately dumb**: toolchain setup, login, metadata, build/push only. **Callers own triggers, guards and tag policy** — each workflow passes its own `registry`/`image_name` (from its `env`), `token`, `push`, `flavor` and `tags`. That explicit local policy is what guarantees a dev build cannot move `latest`. **Never add a `mode: release|dev` input, or any ref/branch logic, to the action.**
- The optional `file` input (default `./Dockerfile`) selects which Dockerfile to build; it exists so the mock job can build `Dockerfile.mock` without a second composite action. **The hub callers must not pass it** — omitting it is what keeps the hub path byte-identical, and the default is the contract. This is a build-input selector, not ref or tag logic, so it does not breach the "stays dumb" rule.
- `flavor` and `tags` are **required** inputs. `publish.yml` passes `latest=auto` (metadata-action's default; a `v*` tag push moves `latest`), `publish-dev.yml` passes `latest=false`.
- Composite actions cannot reliably read the `secrets` context — the token arrives as the `token` input (`token: ${{ secrets.GITHUB_TOKEN }}` from each caller; both keep `packages: write`). `push` is a string: the action compares `inputs.push == 'true'`.
- `.gitignore` allowlists `.github/actions/**` explicitly (mirroring `!.github/workflows/**`). A new file under `.github/actions/` that falls outside that pattern is silently uncommittable, which breaks both workflows in CI.
- actionlint lints the two workflows but **not** the action file — it parses explicit file arguments as workflows (rhysd/actionlint#401).

## Local verify/build prerequisites

- `scripts/verify-release.sh` and a local `docker build` need **bash, git, and jq** (the script parses JSON with `jq`), plus GNU `grep`/`sort`. Windows contributors run under **WSL**.
- Materialize the four siblings as transient clones **inside this repo** (they are gitignored — never vendored):
  ```bash
  for r in mushpi-server mushpi-client mushpi-grow mushpi-mock; do
    git clone https://github.com/mushroom-pi/$r.git
  done
  ```
  A local verify can instead clone from working trees. Plain self-hosting needs none of this.

## `docker-compose.override.yml` & local `.env`

- `docker-compose.override.yml` is untracked by design: it switches compose from pulling the published image to building locally. Self-hosters' clones never contain it.
- Copy `.env.example` → `.env` before a local `docker compose up`. `.env` is gitignored and never committed.
- **A local build can silently run a stale published image.** In build mode the image is tagged from the base file's `image:` field, so if `MUSHPI_IMAGE_TAG` names a tag already present locally (e.g. a pulled `0.9.0-alpha`), `docker compose up -d` skips the rebuild and starts the old image. Use a private tag for local verification (or force the rebuild) so you are testing the tree you built.

## Host networking (`network_mode: host`)

- The `mushpi` service runs on the **host network**, and there is deliberately **no `ports:` block — that absence is load-bearing.** Compose treats `ports:` together with `network_mode: host` as incompatible (current Compose v2 warns and discards the mapping; some versions error), so never "restore" the published port as a cleanup.
- Why it is **required, not a preference**: the server reaches growing units at `http://<handle>.local:<port>`, and on Docker's default bridge that path is dead — the container cannot send or receive LAN multicast, so `.local` never resolves and only the announced-IP fallback carries the poll. Host networking is what puts the container on the LAN.
- Consequence: the server binds the hub's port 3000 **directly on the host**. A host service already listening on 3000 collides at boot (previously the clash surfaced as a port-publish error). The image `HEALTHCHECK` is unaffected — under host networking the container's `127.0.0.1` is the host's loopback.
- **No network isolation.** The container shares the host's entire network stack and can see every host interface and all of its traffic. Accepted for a single-purpose appliance; do not describe the trade-off as free.
- Host networking is **Linux-only**; Docker Desktop for mac/Windows does not provide it, so the build-mode override does not behave the same there. The override's `build:` block still merges cleanly with `network_mode: host` and runs in the host namespace.

## Container mDNS resolver (`.local` unit names)

- The image carries its **own mDNS resolver** so the server can reach growing units at `http://<handle>.local:<port>` without depending on anything the self-hoster's host provides. It is a **query-only** daemon: `[server] enable-dbus=no`, `use-ipv4=yes`, `use-ipv6=no`; `[publish] disable-publishing=yes`, `disable-user-service-publishing=yes`; `[reflector] enable-reflector=no`. **Never re-enable publishing**: the container shares the host's network namespace, so a second responder claiming names would collide with the host's own mDNS stack.
- The entrypoint starts it as root before the privilege drop; it daemonizes, and `dumb-init` is PID 1 so its exit is reaped. **A failed start is logged, never fatal** — the server still boots and the announced-IP fallback carries the poll. Nothing supervises the daemon: if it dies, `.local` resolution stops until the container restarts.
- The NSS wiring uses the **full `mdns4` plugin, not `mdns4_minimal`**, together with `/etc/mdns.allow` listing `.local.` and `.local`. The `_minimal` variants first send an SOA query for the `local` domain to the configured DNS server, which adds latency and misbehaves when that server does not answer `NXDOMAIN`; the allow-file makes `.local` authoritative for the plugin with no unicast-DNS pre-check. The `hosts:` line must be written unconditionally — do not rely on the package's post-install to have inserted a particular spelling, since a silent no-op there yields "resolver running, nothing resolves".
- The daemon runs **without its chroot step** (its default chroot is a container friction point and buys nothing here).
- Verify resolution **as the user the server runs as**, not only as root: `docker exec --user node <container> getent hosts <handle>.local`. A root-shell check can pass while the app still fails on the resolver socket's permissions.
- The alternative shape (not built) borrows the **host's** resolver instead: install only the NSS client and bind-mount the host's resolver socket. It is smaller but host-dependent — it silently degrades wherever the host does not run one. The divergence is confined to the Dockerfile packages, the entrypoint's start step and one compose volume.

## Demo stack & the mock image

- **Shape.** The demo compose is **base + overlay**: `docker-compose.demo.base.yml` holds the service definitions, `docker-compose.demo.yml` is the published-image overlay (the default) and `docker-compose.demo-local.yml` the local-build overlay (§Local demo stack). It is **additive** — it defines its own bridge network and never touches `docker-compose.yml`, the hub `Dockerfile`, or the hub publish job. `scripts/demo-stack.sh` is the single documented entry point; it resolves the announce secret, generates the mock's JSON config (mode 600, never committed), ensures the data dir, then runs `docker compose -f …base.yml -f …<overlay>.yml up "$@"` — and on the **detached** path also verifies the seeded history before exiting. It prints which mode is active, and the verifier one-liners it prints carry the same file pair, so a pasted command talks to the stack that is actually running. `-f docker-compose.demo.yml` alone now renders two image references and nothing else.
- **The published overlay's mock `build:` block is intentional, not an oversight.** `ghcr.io/mushroom-pi/mushpi-mock` has no usable published tag yet, so that `build:` is what lets a laptop with the transient clone start the demo without one (see the "no published mock tag" bullet below). It reads as a stray build in a file whose job is "just image references"; do not delete it as cleanup while the tag gap stands — and note it builds from **this repo's root** context, not the parent; the parent-context mock build belongs to the local overlay.
- **`.env` is optional: the secret resolves from the file *or* the ambient environment.** The demo service has **no `env_file:`** — removed deliberately, because it made a `.env` file mandatory (Compose hard-errors on a missing `env_file` target, so the stack could not start at all without one) and because it injected *every* unrelated hub key from `.env` into the demo container (`MUSHPI_DATA_DIR`, `MAX_REQUESTS`, `DOCS_USERNAME`, `DOCS_PASSWORD`…). `PICO_ANNOUNCE_SECRET` is now interpolated as `PICO_ANNOUNCE_SECRET: ${PICO_ANNOUNCE_SECRET:-}`, which Compose resolves from `.env` **and** the ambient environment: a laptop is unchanged, and a hosted deployment can inject the secret platform-side. **Where a hosted deployment gets that secret is deliberately undecided here** — it is a deployment-target question, and the same reason `.demo-mock-config.json`'s write path is still hardcoded. Keep both supply paths working; do not pick a mechanism in this repo.
- **`docker compose config` inlines `env_file` into the rendered `environment:` map and emits no `env_file:` section at all** (Compose v5.6.0). So "did removing `env_file` work?" cannot be answered by grepping a render for `env_file:` — prove it by the *absence of unrelated keys* (a `DOCS_PASSWORD` from `.env` must no longer appear), or by rendering with **no `.env` present** and confirming it still succeeds.
- **The mock is packaged from *this* repo, not from `mushpi-mock`.** `Dockerfile.mock` builds `mushpi-mock/` as a *build input*, exactly as the hub builds `mushpi-server/` and `mushpi-client/`. The `mushpi-mock` repository receives **no packaging changes** — it has no Dockerfile and no GHCR workflow, and it does not need one. If you find yourself adding either to that repo, the work is in the wrong place.
- **A demo stack needs no published mock tag to come up.** The `mock` service carries both `image:` and `build:`, so `up` builds locally when the tag is absent while hosted deployments `pull` the published image. The `mushpi` service carries `image:` only, matching the hub path. Default is pull-first; pass `--build` to force a local build.
- **Subnet and announce IP are a coupled pair.** The demo bridge uses a fixed subnet (`172.28.0.0/24`) and the mock a fixed `ipv4_address` (`172.28.0.10`) which `demo-stack.sh` writes into the generated config as `announce_ip`. Change one without the other and announces point into nowhere. Deterministic addresses are required because the server reaches units by announced IP on this path. The subnet is deliberately a `/24` (the first draft's `/16` was needlessly wide) and is a common Docker range — re-check for collisions before changing it.
- **The mock's container contract:** config mounted read-only at `/app/config.json`, `command: start --config /app/config.json` (no seeding flag — see below), UID/GID 1000 so the *same* bind-mounted `/data` as the hub image stays writable. The mock serves all five units from **one process** on ports 5000–5004 and binds `0.0.0.0`, which is what makes it reachable across the demo bridge. Its `--seed-days` flag still exists as a standalone developer tool; the demo stack simply no longer passes it.
- **The server owns demo reading-seeding; the mock seeds nothing.** `SeedService.onApplicationBootstrap` runs recipes → units → batches → readings in-process, and the demo stack passes it `SEED_ENABLED` and `SEED_READINGS_DAYS` (pinned to 15 in compose, overridable from `.env`). Two schema facts matter here: `SEED_READINGS_DAYS` is `integer().min(1)` with a compiled default of **14**, so the compose pin is what makes the demo 15, and **`0` is a boot validation error, not an off switch** — disable seeding with `SEED_ENABLED=false`, which the script treats as "skip verification". The readings phase is insert-only and idempotent per unit (a watermark: `COUNT(*) … ts <= seedEnd > 0`), writes `days × 1440` rows at a 60s cadence for `tent-one` … `tent-five`, and applies the drift walk to `tent-three`. `tent-six` gets none. Do not reintroduce a second seeder: the mock's insert-only series overlapped the same handles on a near-identical minute grid, roughly doubling rows and muddying `tent-three`'s drift curve.
- **Seed verification is part of the entry point, on the detached path — because a failed seed is silent.** Seeding failures are caught and logged (`Demo seeding failed: …`) without blocking boot, so an unseeded stack looks like success: empty charts and an unread log line. `demo-stack.sh` calls `verify_demo_seed()` after a detached `up`: it polls `docker compose … exec -T mushpi node -e …` for up to ~30s, opening `/data/app.sqlite` **read-only** with the image's own `better-sqlite3` (no host-side `jq` dependency), and asserts **three** things about the demo profile: (1) every live handle (`tent-one` … `tent-five`) holds **exactly** `SEED_READINGS_DAYS × 1440` readings inside a **data-anchored window** — `lo = MIN(ts)` for that handle (always the seed's own `startTs`; live poll rows are strictly later) and `hi = lo + (expected − 1) × 60s`, counted inclusively, so the 60s poll's later rows cannot flake the count while a whole-table equality would. The window is **never** recomputed from `Date.now()`: the seeder freezes `seedEndTs` at boot, so a clock-derived cutoff slides forward on the next minute boundary, drops the oldest seeded row, and fails a healthy seed at `expected − 1` (the original 21599 bug). A handle with no rows fails explicitly, naming it; (2) `pico_unit` holds **exactly** the six seeded handles (`tent-one` … `tent-six`) — which is what catches a mock announcing a handle the server never seeded, since that damage surfaces as a *seventh* row rather than a missing one; (3) in-progress batches sit on `tent-one` … `tent-four`, **including** the drifting `tent-three` and **excluding** the offline `tent-six` (`tent-five`'s only seeded batch is planned). It fails **non-zero** with the per-unit counts plus the roster and placement lines and a `logs mushpi` pointer that names the `Demo seeding start — boundary …` / `Demo seeding complete` lines to check. The **foreground path cannot do this**: the script `exec`s into compose and hands over the terminal, so it prints an equivalent pasteable one-liner instead. That asymmetry is inherent, not an oversight.
- **Seed verification is followed by a separate announce/poll identity check** (detached path only). `verify_poll_identity()` polls for up to ~150 s — the cron is every 60 s and the first tick can land a full interval after `up`, so the seed's 30 s deadline is too short here — and asserts, for the five mocked handles only (`tent-six` is intentionally offline): `pico_unit.ip` is non-NULL **and** at least one reading exists with `ts > now − 150s` (two poll intervals). The live-reading assertion is deliberately end-to-end: the poll target is built from the announced `ip` **and** the stored `port`, so a stale seeded `port` breaks polling even when `ip` is correct. Its failure text is a distinct class from the seed's and never mentions seeding — it points at `Pico unit N unreachable (… tent-X.local …)` in the `mushpi` log, i.e. the server falling back to mDNS because the announced identity was not persisted. It runs regardless of `SEED_ENABLED`.
- **The verifier's SQL is tied to real schema names:** `pico_unit`, `readings`, `batch`, `pico_unit_id`, `handle`, `start_at`, `finish_at`. These were confirmed against the server's entities, its `InitSchema` migration *and* an empirically synced throwaway database, then exercised end-to-end against a live-synced DB. A server rename therefore degrades the check into a FAILED report rather than a crash — keep them in step. "In progress" mirrors `Batch.status` (`start_at` already past, `finish_at` null-or-future); dates are compared as **TypeORM's UTC string** (`YYYY-MM-DD HH:MM:SS.mmm` — fixed width, milliseconds zero-padded to three by `DateUtils.formatMilliseconds`), so lexicographic comparison against the same shape is exact and no `julianday()` parse or timezone interpretation is needed. **Live poll rows carry second-precision `ts`** (the DB default `CURRENT_TIMESTAMP`, no `.mmm`) while seeded rows carry milliseconds; both are fixed-width and prefix-comparable, so `MIN(ts)` anchoring and lexicographic comparison still hold. The verifier JS is deliberately **"!"-free** (`seedOk===false`, `indexOf("tent-six")<0`): the foreground path prints that same JS as a pasteable **double-quoted** one-liner, and a `!` inside it fires interactive history expansion in the operator's shell.
- **A demo volume older than the handle rename fails the roster check on purpose.** The mock used to announce `mock-tent-*`; the server upserts by `handle` and **never deletes**, so those rows survive as orphans and the exactly-six-units assertion goes red. A volume that also predates the seed-ownership move can additionally carry a **doubled readings history** — the old mock series overlaid on the server's — which the window-scoped exact count catches instead. No code in this repo removes data — the remedy is the operator's own: `down` the stack and delete the disposable `MUSHPI_DEMO_DATA_DIR` (never the hub's `MUSHPI_DATA_DIR`).
- **`SEED_READINGS_DAYS` (15) lives in two places that must agree:** the compose interpolation on the `mushpi` service and the script's `SEED_READINGS_DAYS` global. The server's compiled default is **14**, so the compose pin is what makes the demo 15 — drop it and charts silently shorten. `0`, negatives and fractions are boot validation errors; the disable switch is `SEED_ENABLED=false`, which also skips verification. Because the mock no longer seeds, `tent-three` carries **only** the server's drift walk — the drift series is clean by construction, and any future second seeder would muddy it again.
- **The server runs SQLite without WAL** (rollback journal; `busy_timeout` is better-sqlite3's 5 s default, not set by app code), so concurrent writes queue rather than fail instantly. The demo path's writers are all inside the server process (boot seeding vs the 60 s poll), and a lock would abort a whole 500-row insert chunk — never exactly one row. **Do not attribute an `expected − 1` count to locking**: that shape is the clock-derived-window bug described above, and the verifier no longer suggests a lock. Enabling WAL would be a **server-side** change — flag it, do not hack around it here.
- **Two facts in `Dockerfile.mock` belong to another repo, and both are build-guarded — keep it that way.** The console-script name (`[project.scripts] mushpi-mock`) and `mushpi-mock`'s `requires-python` are owned by that repo's `pyproject.toml`, so `Dockerfile.mock` runs `RUN mushpi-mock --help` after `uv sync`: a rename or a broken import fails the **build** instead of producing a container that dies at start. `requires-python` needs no separate guard *only because* `uv sync --frozen` runs under `UV_PYTHON_PREFERENCE=only-system` — remove that and uv will happily fetch a different interpreter, the build will pass, and the guard silently disappears. If you add a third borrowed fact, guard it the same way rather than trusting it.
- **`NODE_ENV=demo` requires exactly six rate-limit variables, plus a non-default secret.** The six are the `VISITOR_*`, `ABUSE_*` and `GLOBAL_*` `MAX_REQUESTS`/`MAX_REQUESTS_TIME` pairs — three all-or-nothing pairs, windows in **milliseconds**; the server refuses to boot if any is missing, and also if only one half of a pair is set. `PICO_ANNOUNCE_SECRET` must be present and must not be the dev default. Nothing else is required: `CLIENT_URL` is optional in demo (required only in `local`) and `CLIENT_DIST_DIR` only in `prod`.
- **There is no announce-lockout configuration — never invent one.** The demo announce guard is **origin-gated, not budget-gated**: it refuses externally-originated announces with a 403 with no env vars, no budgets and no state. A dead `DEMO_ANNOUNCE_*` triple (guessing-per-minute, its `_GLOBAL` twin, and lockout-minutes) was briefly passed through this stack; none of the three ever existed in the server's schema, and a silently-ignored variable is indistinguishable from a working one because the server validates with `allowUnknown: true`. Take the authoritative set from `mushpi-server`'s `config.schema.ts` or its generated `docs/ENVIRONMENT.md` — **never** from a local `.env.*.local` scratch file, which is exactly what misled an earlier pass on this repo and put three phantom requirements into the demo compose file.
- **`/health` is exempt from throttling but `/ping` is not.** The image `HEALTHCHECK` targets `/ping`, so a demo stack counts one health request per interval against the visitor limit. Negligible at the shipped defaults; revisit if the limits are tightened.
- **⚠ No published image can boot `NODE_ENV=demo` yet — full-stack demo E2E is therefore blocked, and not by this repo's packaging.** The demo profile lives in `mushpi-server` HEAD but has never shipped in an image, and `publish.yml` has never executed, so neither `ghcr.io/mushroom-pi/mushpi-mock` nor a demo-capable `mushpi` tag exists remotely. Direct probes of the published `0.9.0-alpha` and local images all fail config validation (`NODE_ENV must be one of [dev, local, prod, staging, test]`). The first real end-to-end run happens only after a publish from `main`. Do not read a green `docker compose config` as proof the stack runs.
- **First publish creates the GHCR package.** The `mushpi-mock` package does not exist yet; the first `build-and-push-mock` run creates it, which requires the org to allow package creation for `GITHUB_TOKEN`. A red first run with a 403 here is a settings problem, not a workflow bug.
- **`publish-dev.yml` has no mock path.** A dev/pre-release build publishes the hub image only, so there is no dev-tag mechanism for the mock. Open gap — decide deliberately rather than assuming the mock follows the hub's dev tags.
- **Verify a local mock build with the sibling present**: `git clone` `mushpi-mock` into this repo (transient and gitignored, per §Local verify/build prerequisites), then `docker build -f Dockerfile.mock .`.

## Demo reset

- **The reset is a restart, because the server already owns the wipe.** `scripts/demo-reset.sh` runs `docker compose … restart` on both demo services and nothing else — no `down`, no external data-directory wipe, no `demo-stack.sh -d` re-run. `mushpi-server`'s `cleanStart()` unlinks the SQLite file (with its `-wal`/`-shm`/`-journal` sidecars) and the image tree on **every demo boot**, gated by a `.demo-owned` marker that survives so the next boot wipes again, and it runs before TypeORM connects. An external `rm -rf` duplicates that work and races an open handle; it is not a safety net, it is a second writer.
- **Both services restart — a server-only restart is deliberately not the optimisation it looks like.** Clean-start leaves a fresh DB whose re-seeded units carry `ip = null` and `port: 5000`, and mDNS is dead on the demo bridge (§Demo stack: the announce *is* the address path). A restarted mock re-announces on boot via its retry ladder (4 attempts, ~45 s) and the server is listening well inside it. A mock that never restarted would only recover via its poll-aware watchdog at **180 s of silence**, so a server-only reset shows seeded batches with every unit `offline` for two to three minutes — neither a working demo nor a "resetting" message.
- **The intended fix for that gap was evaluated and dropped, not overlooked.** Seeding demo units with the mock's fixed bridge address (env-var driven, so the compose file stays the single source of the IP) would make units addressable before they announce and would close the gap entirely. It was scoped out of the nightly reset because it is a `mushpi-server` change with its own cross-repo semantics; a ~3-minute recovery after an unplanned server-only restart was judged acceptable for the demo. Do not "improve" `demo-reset.sh` into a server-only restart on the assumption that announce is redundant.
- **The guard exists to keep the reset off a real hub, and it must never print the render.** It renders the active compose pair and refuses unless the render contains both `NODE_ENV: demo` and the `mock` service, and refuses if `MUSHPI_DEMO_DATA_DIR` resolves to the same path as `MUSHPI_DATA_DIR`. **`docker compose config` inlines `PICO_ANNOUNCE_SECRET`**, so a failure message names *what is missing* and never dumps the render; only compose's own error text is safe to print, because it names files rather than values. `realpath -m` is used rather than `readlink -f`, which fails on the legitimately absent hub directory on a demo-only host.
- **`docker compose restart` has no `--wait` and no `depends_on` health gate**, unlike the `up -d` path the stack entry point uses. Without an explicit wait, the seed verifier's 30 s window starts against a cold container and a healthy reset reads as a failure — so the script polls `docker inspect --format '{{.State.Health.Status}}'` with a bounded timeout first. The unit's `TimeoutStartSec=900` is sized to the worst case (health wait + seed window + the poll verifier's 150 s deadline); systemd's 90 s default would kill every run mid-verification.
- **The timer must not `Requires=` its own service.** That pulls the oneshot into the transaction at `enable` time and would fire a wipe-and-reseed immediately; `[Install] WantedBy=timers.target` is what makes `enable` work at all.
- **The shared verifier is `scripts/demo-verify.sh`, and it serves two callers.** The stack entry point and the reset run byte-identical assertions (seeded history, roster, batch placement, announce/poll identity) — they were extracted from `demo-stack.sh` rather than copied, and `DEMO_VERIFY_TAG` is what keeps the stack path's message text unchanged. It adds a fourth check, `verify_demo_owned`, asserting the `.demo-owned` marker **inside the container** at the path clean-start uses, so it cannot drift from the mount. That check is run-mode only; `--print` output is unchanged.
- **The verifier's deadlines bracket the mock's recovery ladder on purpose.** The seed window is 30 s, the poll-identity deadline 150 s, and the watchdog re-announce lands at 180 s — so a reset whose seeding overruns the announce ladder reports **FAILED** instead of passing on a watchdog rescue that arrived after the assertion gave up.
- **The reset does not regenerate `.demo-mock-config.json`.** Regenerating it is `demo-stack.sh`'s job because it validates the announce secret first. So after a `PICO_ANNOUNCE_SECRET` change the nightly reset re-announces with the **stale** secret and the poll-identity check fails until `demo-stack.sh` is re-run by hand. This is the one operator trap in the reset path.
- **No image pull, by design.** The reset restarts whatever image is already present; a bad release must never land unattended at 03:00. Updating the demo is an explicit operator action.
- **`.env` still wins over the ambient environment** in the extracted verifier, matching the entry point's existing precedence. That quirk was preserved rather than fixed during the move — changing it would alter how both callers resolve the secret.
- **`MUSHPI_DEMO_RESET_STATUS_FILE`** (default `./mushpi-demo-reset.status`, gitignored) carries the last successful reset's ISO 8601 UTC stamp; the same line also goes to stdout for journald. The systemd unit's `/opt/mushpi-ops` paths are install-time placeholders.

## Local demo stack (parent-context builds)

- **What it is.** `scripts/demo-stack-local.sh` builds `mushpi:demo-local` and `mushpi-mock:demo-local` on the developer's machine from the working copies at `../mushpi-server`, `../mushpi-client` and `../mushpi-mock` — **uncommitted changes included** — and runs the same demo stack on `http://localhost:3000`. No GitHub run, no registry, nothing pushed or pulled. This is the only way to exercise `NODE_ENV=demo` end-to-end before a publish: the demo profile lives in server HEAD and no published image can boot it (§Demo stack). The wrapper only checks the sibling layout and sets the internal switch `MUSHPI_DEMO_LOCAL` (never a user-facing knob — do not document it as one, and do not tell a reader to export it); mode selection, secret resolution, config generation, `up` and both verifiers stay in `demo-stack.sh`, so the two modes cannot drift.
- **A local build is still a demo, not a development environment.** Both overlays carry the same `NODE_ENV=demo` profile, so the dashboard stays read-only: every write is refused with `403` except Pico announce (no batch creation, no recipe editing, no unit management). The local overlay changes only where the image code came from — do not describe it as a dev setup, do not route a "edit the data" workflow through it, and do not expect interactive seeding or admin actions to work there. Legitimate uses: confirm uncommitted working copies still produce the showcase, and exercise the `demo` profile end-to-end. Write-capable development happens outside this stack, in the server's own dev/local profile.
- **Parent context.** Both local overlays set `context: ..` (the directory holding this repo) with `dockerfile: mushpi-ops/Dockerfile[.mock]`. Compose resolves `dockerfile:` **relative to the context**, which is why the path is repo-qualified; `config` renders `context: <parent>` + `dockerfile: mushpi-ops/Dockerfile` and BuildKit then reads the `<dockerfile>.dockerignore` sitting beside that Dockerfile. Verified: a parent-context hub build transfers a few MB, not the ~1.4 GB the unfiltered tree would be.
- **`MUSHPI_OPS_PREFIX`.** From a parent context, this repo's own files are one level down, so the two COPYs that read them (`release.json`, `scripts/docker-entrypoint.sh`) go through `ARG MUSHPI_OPS_PREFIX`, default `.`, passed as `mushpi-ops` by the local overlay. The ARG must be re-declared per stage — stage scoping is the trap. The default keeps CI/release builds identical: `COPY ./x` and `COPY x` produce the **same layer diffID** (BuildKit normalises the path; only the per-build `created` timestamp changes the repo digest), and `mushpi-server/` + `mushpi-client/` need no prefix because they are children of either context root. `Dockerfile.mock` takes no prefix at all.
- **Both halves of the `release.json` coupling are now prefix-bound.** The §Build-context-layout note (Dockerfile COPY **and** non-ignored file) still holds, but breaking the prefix breaks it: with a wrong `MUSHPI_OPS_PREFIX` the build fails loudly (`COPY source … not found`) instead of silently showing the `dev` footer.
- **Local-only tags.** `mushpi:demo-local` / `mushpi-mock:demo-local` are deliberately unqualified so they resolve to no registry — they can never be pushed by accident and never shadow a published tag. The §`docker-compose.override.yml` stale-tag trap applies: `up` does **not** rebuild an existing tag, so pass `--build` (or `build` first) to pick up working-copy edits.
- **Layer caching / single-service rebuild.** Per-Dockerfile ignore files keep the contexts disjoint for what matters, and the hub's ignore list excludes `mushpi-mock`. Observed: with a change under `mushpi-mock/src`, `build mushpi` is fully CACHED while `build mock` invalidates only from `COPY mushpi-mock/src` onward (`uv sync` and the `mushpi-mock --help` build guard re-run, which is that guard doing its job). Use `docker compose -f …base.yml -f …demo-local.yml build mock` for mock-only iteration.
- **Ports.** `MUSHPI_DEMO_PORT` moves the hub port (container side stays 3000). The mock's five host ports are **not** configurable: `docker-compose.demo-local.yml` hardcodes the same loopback `5000-5004:5000-5004` mapping the published overlay uses, because the container side must stay 5000-5004 and Compose cannot do arithmetic — a developer who needs different mock ports edits the overlay. Port 3000 genuinely collides with a hub container, another checkout's demo, or a `yarn start` — the override (or stopping the other listener) is the answer, not a claim that the collision cannot happen.
- **Verification without touching live demo state.** The entry point sources `.env` *after* the ambient environment, so an exported `MUSHPI_DEMO_DATA_DIR` is overridden by `.env`; to test the stack without writing into an existing `mushpi-demo-data`, invoke compose with `--env-file <throwaway>` instead of the script. Never run against the hub's `MUSHPI_DATA_DIR` (§⛔).
